# Module-First 开发方法论

> 总纲：**人的验证精力是唯一稀缺资源；AI 产能近乎无限但不完全可靠。所有规则的目的都是降低每次变更所需的人工验证成本。**

## 场景速查

> 规则是判断依据，不是答复内容：回答里不出现规则编号和表名，不把这里的阈值、清单当成用户项目的既定事实，用户没提到的条件不要假设。

| 现在要做的事 | 执行 |
|---|---|
| 开新项目 / 搭骨架 | 按确定度划结构：已存在的边界划出来，计划中的留位，想象的不留（规则 6）；写契约并核对上下游（规则 4）；附加机制等信号（首日清单） |
| 加新功能 | 先问契约要不要变（规则 3）：不变就改模块内部，要新契约才新增模块；再定变更级别（规则 8） |
| 改既有模块 | 按规则 8 定级：内部修改、兼容扩展直接动手，破坏性变更同批迁完 |
| AI 产出验收 | 三层验证（规则 11），人只看接口 diff 和运行结果；同批产物连坐复查（规则 10） |
| AI 产出有缺陷 | 规则 9：成熟库能替代吗 → 最小复现确认缺陷在模块内 → 换生成条件重写，契约和失败用例先固定 |
| 多 agent 并发派工 | 先判断规范能否成文（规则 16）；上下文给足、汇报压短（规则 14） |
| 例行健康检查 | 上帝模块信号（规则 7）+ 缺陷注入演练（规则 13） |

## 元规则

1. **规则按收益存废。** 每条规则存在的理由是减少人工验证量，维护成本超过节约量的删。这也适用于本文：除总纲、本节和「契约要对得上」（规则 4）之外，其余都是默认值，按领域清晰度、验证成本、项目寿命调紧或调松——一次性原型可以只留冒烟门禁。
2. **给项目定的规则必须可自动检查。** 依赖自觉遵守的规则形同虚设。定规则时同时写明机器怎么校验、出现什么现象说明它已失效该删。

## 模块

3. **模块是变更的基本单位，契约稳定是内部可以放手改的前提**——这就是模块化的全部收益。新需求先问契约要不要变：不变，就在既有模块内部改；需要新的输入输出契约（新的、独立变化的职责），才新增模块。预留位置的取舍见规则 6。
4. 每个模块声明**输入、输出**（schema）和**依赖了哪些模块**；只声明「我依赖谁」，「谁依赖我」由工具推导。schema 里每个字段附真实示例和语义说明（如 `userId: "usr_8f2"`，对外暴露的 ID）——光有类型防不住两个模块对同一字段理解不一致。**跨模块契约要对得上**：下游要算的量，上游得以可计算的类型给出（数量存成自由文本，下游就没法做算术）；契约写完先核对这一步，比写完代码再发现便宜得多。
5. 依赖声明分两层。**事实层**（实际 import 了谁）：每次构建与代码自动比对，不一致即失败，首日就上。**边界层**（允许依赖谁）：等信号出现再改为 lint 强制（按需升级表）。
6. 结构按确定度分级：**当前已存在的领域边界首日就划**——领域越清楚、后期拆分越贵，越值得先划；**已列入计划的方向可以先留位**——留位的成本决定留法：空模块目录、契约里预告的接口几乎免费，可以留；跨模块字段预留会让契约无声变宽，等真做时再加；**纯想象的可能性不留**。划错了按规则 8 改。配两项自动检查：循环依赖→构建失败；某模块只是原样转发依赖的输出→提示它可能不必存在（模块的输出应当是自己领域的形状）。
7. 自动检查抓不到的劣化：**某个模块逐渐承担所有职责**。它各项指标都好看，实际是最大的风险点。两个可统计的信号：反向依赖数远高于其他模块；出现在大多数变更的 diff 里（git log 按路径统计）。编排层天然满足这两条，对它要另看：是否长出了业务判断。

## 变更（四级，逐级升格）

8. **变更分级**：
   - **内部修改**（不碰输入输出）→ 直接改，其他模块零感知。最常见，也最便宜。
   - **兼容扩展**（加可选字段/新接口，旧调用方无感）→ 直接加，无需同批迁移；判据：现在就有使用方的可以加；计划中的方向按规则 6 在结构层留位，不在字段层预留。可选字段的删除信号：grep 不到读取方，或删掉后类型检查不报错——发现即删。
   - **破坏性变更**（改语义/删字段/可选变必填）→ 显式地改，同一批次迁完所有调用方，不留兼容层（兼容层的堆积就是技术债）。首选让类型不兼容、由类型检查器列出未迁移处；但报错清零只是必要条件——字符串拼接、序列化、动态取值这些路径它看不见，再按字段名 grep 一遍。存量数据怎么迁到新形状、缺失值取什么默认，是方案的一部分。
   - **整体重写** → 不是变更手段，是缺陷处置手段，见规则 9。
9. **先复用，再生成；修不好就换条件重写。**
   - 复用阶梯：真的需要吗 → 代码库里已有？→ 标准库或平台原生？→ 已装依赖里有？→ 一行能写完？→ 都不是，才引新库或让 AI 生成。有公开规范的领域（解析器、日期、编码）整库引入不自研；单个工具函数别为它引整库。
   - AI 产出的模块反复修不好，先按上面这一遍看能否直接换成熟库；不能，再整体重写——通常比继续修补便宜。重写前用最小复现用例确认缺陷确实在该模块内部（而非依赖、配置或上游数据），没确认就重写是浪费。
   - 重写必须更换生成条件（改写提示或更换模型）：相同输入重新生成，大概率复现相同缺陷。既有契约和已知失败用例作为重写的输入固定下来，否则又是一次盲抽。三次仍不通过，转人工。
10. **同一批指令生成的代码视为同一批次**：一处查出缺陷，全批次复查，它们可能带着相同的系统性错误。

## 验证

11. 验证分三层：**模块内部测试**随实现产生；**接口测试**按契约校验真实输出，在接口有两个以上调用方时补上（按需升级表）；**人工验证**只看接口变更和最终运行结果，不逐行读实现。
12. **实现方 AI 不得修改验收它的测试**——端到端冒烟、接口测试、规则 9 固定下来的失败用例；模块内部测试随实现一起改。落地靠 CI 检查变更路径：验收测试放独立目录，实现类变更的 diff 触及该目录即失败；改验收测试单独开一次变更、单独审查。CI 同时封禁类型逃逸（`as any`、`# type: ignore`）和跳过测试。
13. 定期做**缺陷注入演练**：故意埋入缺陷（如互换两个字段的语义），看测试和告警能否捕获。捕获不了先修检查机制——**失灵的检查比缺陷本身更危险**，它给的是虚假的安全感。

## 协作

14. **给 AI 的上下文尽量充分**（模块文档、相邻接口一并给）；**AI 的进度汇报尽量精简**（只报异常）。设计说明、方案建议是交付物，不在压缩范围内。
15. 能在编排层统一处理的（日志、超时、限流）统一处理，不在各模块重复实现。无法统一处理的（操作是否幂等、权限语义）由模块在接口中显式声明，编排层据此执行策略。**好的模块划分让横切关注点不需要横切。**
16. 多个 AI 并发修改前，先判断本次变更的规范**能否成文**（术语表、字段格式）。能成文则先定规范再并发；不能成文的（性能、全局一致性）不适合并发，由编排层统一把关。

## 按需升级

初始不引入附加机制，出现对应信号时再启用：

| 信号 | 启用 |
|---|---|
| 两个模块对同一字段理解不一致，造成返工 | 引入专用类型（外部 ID 与内部 ID 定义为不同类型，混用即编译失败） |
| 第二个 AI 并发开工，或发生越界访问 | 依赖**边界层**（允许依赖谁）改为 lint 强制 |
| 某接口拥有两个以上调用方 | 为其补接口测试 |
| 单次变更的人工验证量超出承受范围 | 强制拆分批次 |

## 新项目落地清单（首日）

1. `git init`（规则 7 的统计靠它）
2. 按确定度划结构（规则 6）；每模块一份契约文件——输入/输出 schema + 依赖声明——放模块目录内；核对上下游对得上（规则 4）
3. 上免费的强制项：严格模式的类型检查（tsc strict、mypy --strict 或等价物）、循环依赖检测、依赖声明与实际 import 的比对（规则 5 事实层）
4. 门禁 = 构建通过 + 主流程端到端冒烟
5. 其余等信号（按需升级表）——**首日过度配置与不配置同样是错误**

## 首个验证实验（对方法论本身）

半天，在用后即弃的分支上：由 AI 搭三个模块，**注入三类典型缺陷**——职责过度集中的模块、绕过依赖声明的隐式耦合、同一字段两处语义不一致——统计现有检查机制的捕获率。**捕获率就是这套方法论当前可信度的实测值。**
