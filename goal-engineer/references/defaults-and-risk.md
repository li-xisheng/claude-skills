# 默认值、风险分级与提问题库

可靠性不来自懂每个领域,而来自:保守默认、先查权威材料、实证验证、有上限的迭代、高风险暂停。

## 默认值优先

任务模糊但不确定性是低风险的,就选最优默认继续,别让领导填表。好默认:

- 新应用/网站/工具:先做本地 MVP
- 现有仓库:先读项目脚本、文档和惯例
- 没提部署:只做本地运行验证
- 没提账号:不加登录、后端、云同步、付费 API、账号系统
- 没提设计系统:老项目跟现有风格;新项目选克制可用的界面
- 不知道测试命令:先查 package scripts、Makefile、CI 配置、Xcode schemes、项目文档,不发明
- 没提高级功能:实现最小完整的用户可见流程

每次默认都附一句理由,如:「默认选择理由:先做本地 MVP,因为它最快验证核心体验,同时避免账号、后端和发布流程拖慢第一版。」

## 风险分级

- **低风险**:本地原型、本地 UI、本地文档、玩具数据、隔离脚本、非破坏性格式化、生成示例。→ 直接选默认,出可复制目标(轻量档)。
- **中风险**:改现有仓库、对外 UI 文案、开发环境迁移、共享配置、测试凭证的外部 API、浏览器扩展、移动构建。→ 默认仍轻量档:选默认,但边界和暂停条件写实;叠加长时程、多 agent 或验收需设计时才升完整档。
- **高风险**:生产数据、支付、凭证、破坏性删除、法律/医疗/金融建议、合规、隐私敏感数据、版权素材、商店上架、线上部署、账号所有权。→ 要么出编号选择题让领导拍板,要么只出 discovery-only 目标——在危险动作前必须暂停;一律完整档。

## 陌生领域:discovery-first

领域陌生或高度专业化时,不发明领域规则,出「先勘探再动手」的目标:验证字段里写明先盘点工作区里的项目文档、现成脚本、样例数据、领域笔记或官方参考;约束里写明「不许编造检查不到的领域规则、合规声明、数据语义或对用户的承诺」;迭代策略里把 discovery pass 排第一步,写下工作假设再实现最小切片;完成条件写明「第一个工作流在已记录的工作假设下有证据可用,且未解决的领域问题清晰列出」。高风险的破坏性诉求更进一步,用 **discovery-only**:目标止于盘点/dry-run/出方案,危险动作前必停、待领导裁决(完整档写法见 brief-anatomy.md 探索型)。

## 模糊词翻译

不禁模糊的方向词,把它翻译成验证和迭代:

```text
设计方向:克制、专业、有留白,避免模板感和营销页风格。
验证:用桌面和移动端截图检查首屏身份、信息层级、文字可读性、核心入口和布局重叠。
迭代策略:基于截图做最多 3 轮聚焦视觉改进,优先调整层级、间距、字体、素材处理和控件密度。
```

方向词管品味,验证管过不过。

## 迭代默认

「迭代策略:先实现可运行第一版,再基于构建结果、运行日志和截图做最多 3 轮聚焦改进;同一错误连续失败 2 次后必须换证据来源。」禁止「keep trying」「直到满意」。

## 提问题库

只问答案会改变成本、风险、归属或产品方向的。优先编号选择题带推荐默认,领导可回「按默认」或「1B 2A 3C」。

**快速三连**(极模糊但低风险时):

```text
1. 项目形态:A 新建本地 MVP(默认) / B 改现有项目 / C 先做原型
2. 范围:A 核心流程(默认) / B 加常见增强 / C 做完整产品
3. 验证:A 本地运行检查(默认) / B 真机或线上检查 / C 发布前检查
你可以直接回复:按默认,或回复类似 1B 2A 3C。
```

**定向追问**(按缺口挑,别全问):

- 结果:要的是代码改动、文档、发布产物、干净的仓库状态、部署,还是一个验证过的诊断?最终给谁看?第一版能用就行,还是要生产级完整度?
- 验证:项目有没有自带命令(package scripts / Makefile / CI / pytest markers)?需不需要活体验证(浏览器截图、移动视口、API 调用、PR 状态、发布 URL、导出文件)?要补测试还是只跑现有检查?
- 约束:哪些公开行为、文件格式、API 契约、schema、UX 不许变?密钥、凭证、生产数据、用户内容在不在范围内?默认分支禁不禁直推?
- 边界:允许哪些目录?哪些文件、产物、缓存、无关模块不许碰?文档、测试、mock、fixtures 让不让写?
- 迭代:每次改动后要不要重跑检查?连败之后读日志、查文档、缩最小复现,还是暂停?尝试次数/时间/token 有没有预算帽?
- 完成与暂停:什么证据足以停止?什么阻塞必须等人(登录、2FA、付费、破坏性删除、法律/医疗/金融、账号所有权、产品方向)?部分成功要不要交,还是必须跑到全证明?
