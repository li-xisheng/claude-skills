# 深度问题分析

用户想要的不是一个方案，而是**一条能被证据检验的推理链**：问题被重新定义过，结论有现实案例撑着，关键判断写明了什么证据能推翻它，第一步是便宜、可逆的实验。所以严格按五段顺序走，前面的分析不能偷偷预设后面的结论。

这类框架最常见的失败方式是**形式主义**：每个格子都填满了，看起来很严谨，但案例是编的、类比只是表面相似、三位"专家"其实是同一个声音。下面的规则大多是为了防这个。

## 1. 选档与自我调控

档位定义的是**完成标准**，不是次数。查几轮、找几个案例、举几个类比、展开多少篇幅，都由你按问题复杂度、检索收益和可用资源自己决定；判断"够了没有"只看是否达到该档的完成标准。

用户明确说了档位（低/中/高、快速/标准/深挖、quick/standard/deep）就照办；没说就用**中档**。拿不准时看"判断错了的代价"。

| | 低 | 中（默认） | 高 |
|---|---|---|---|
| 什么时候用 | 先摸个底、时间紧、问题本身不大 | 一般的重要决策 | 不可逆或高投入的决策、结论要拿给别人看、用户说"认真查""别漏" |
| 投入方式 | 以已有知识为主；能联网时，有限的检索优先用来找失败案例，因为这一段最容易凭记忆编造 | 联网检索，正反两面都找 | 在中档基础上，用 subagent 并行分路检索、隔离视角、红队反驳，见 [references/high-tier.md](references/high-tier.md) |
| 完成标准 | 给出方向性判断，最影响结论的假设已显式写出 | 关键判断都有证据支撑或已标为推测；专门针对失败、复盘或争议的检索做过，且继续检索已不再带来新案例或新教训；案例检索、跨领域借解、专家会诊这三段各自真的影响了结论 | 关键假设都有正反两面证据；不同检索路线开始命中同一批案例；红队提出的最强反驳已被回应或已写入风险 |
| 关键问题门 | 不提问，用显式假设代替 | 必要时问一个 | 必要时问一个，且在启动检索前问完 |
| 产出 | 对话内，紧凑 | 对话内完整五段 | 完整报告落盘 + 对话内给摘要 |

**档位与可用资源是两回事**。档位是用户要的深度；资源是你实际能动用的东西。不要凭感觉估计自己的"思考强度"，看能观察到的信号：有没有联网和 subagent 工具、上下文还剩多少、用户有没有说赶时间、系统提示里是否给出了推理强度或预算。

- 资源偏紧时，同一档位压缩的是展开篇幅和检索轮数，以下底线不能丢：五段结构完整、关键判断带证据标签、不编案例、停止条件可观测、第一步实验可执行。实在达不到该档的完成标准，就在结尾说明哪一项没做到，不要假装做到了。
- 资源宽裕时，多花的力气用在反例检索、交叉验证和推翻自己的初步判断上，而不是把文字写长。低档仍然要紧凑。

分析中途发现问题比预想的大（不可逆、牵涉多方、有已知的大规模失败先例）时，在结尾建议升档。升到高档的成本明显更高，用户没要求时只建议，不自行升档。

## 2. 整理输入

用户可能填好了模板（问题、已知事实、目标、当前做法、现实约束），也可能只给了一句话。先从对话里抽取这五项，缺的不要逐项追问，直接在第一段把它记为"未经验证的假设"。

如果问题关于当前项目或代码库，先读相关文件和文档：能从代码里查到的事实，不要写成假设。

## 3. 关键问题门

完成第一段（第一性原理）后检查：有没有某个缺失信息，它的两种合理取值会导向**不同的推荐方案**？

- 有 → 中档和高档停下来，只问这一个问题（能给选项时附上选项，以及每个选项会把结论推向哪里），拿到回答再继续。高档必须在启动检索 subagent 之前完成这一步，否则会浪费整轮检索。
- 没有，或缺口只影响细节 → 不问，继续。
- 低档 → 不问，把它写成显式假设，并在结论里标注"若该假设不成立，结论会改为 ……"。

一次只问一个，选最影响结论的那个。不要把多个问题拼成一个长问题。

无法与用户对话时（作为 subagent 运行、无人值守执行），不要停下来等回答：按低档的做法把它写成显式假设，继续分析，并在结论里写明该假设的另一种取值会让结论怎样变。

## 4. 五段分析

每段的具体输出格式见 [references/report-template.md](references/report-template.md)。下面是各段要守住的东西。

### 一、第一性原理

拆成四部分：已确认的事实、未经验证的假设、真正目标、现实约束。

- "事实"只收用户给出的、查证过的、或代码里能看到的内容。用户的判断和推测（"用户不会用""成本太高"）归入假设。
- 真正目标要往上追一层：用户说的目标常常是手段（"要做 X 功能"背后可能是"要降低流失"）。追出来的目标与字面不一致时，两个都写，并说明分析按哪个展开。
- 然后暂时放下行业惯例和现有方案，从这四部分重新定义问题，推导出几条可能路径，其中考虑"不做"或"换个问题解决"。

### 二、现实案例检索

找相同或高度相似的问题、项目、产品和失败案例，回答：别人试过什么、哪些有效哪些失败及原因、反复出现的教训、哪些能迁移、哪些因条件不同不能照搬。

- **主动找反面**：查询里明确用"失败""复盘""postmortem""弃用""踩坑""争议""why we stopped"之类的词。只搜到成功案例时，在报告里写明"未找到失败案例"，这本身是一个需要警惕的信号（幸存者偏差）。
- **来源优先级**：一手资料（官方文档、论文、项目自己的复盘、issue 讨论）> 高质量技术讨论 > 媒体报道 > 营销文章。营销文章只能作为线索，不能单独支撑结论。
- **不编案例**：每个案例要附来源链接；凭记忆写的标【记忆，未核实】。找不到就说找不到。编出来的案例比没有案例更糟，因为它看起来像证据。
- 写清"条件差异"：别人的规模、预算、时代、市场和用户的有什么不同，这决定了能不能迁移。

### 三、跨领域借解

先剥掉行业术语，用一两句话写出问题的底层结构和核心矛盾（例如"两个都想要的东西共用同一个有限资源""反馈周期远长于决策周期"）。再从历史案例和多个距离较远的领域找结构相似的问题（原框架要求至少 3 个领域，低档可以只取最有分量的一两个），每个回答五问：原领域的问题、结构上的相似之处、原领域的解决机制、可迁移的部分、因环境约束不能照搬的部分。

- 相似必须落在**结构**上：能指出双方对应的变量、约束或反馈回路。只是"听起来像"的类比删掉。
- 数量是目标不是配额。有分量的不够时，写明哪个是弱类比，不要硬凑；有分量的很多时，只留能改变结论的那几个。
- 不能照搬的部分要具体到机制哪一环会断，而不是泛泛地说"环境不同"。

### 四、专家会诊

根据前面的分析，选**真正互补、甚至可能冲突**的专业视角。原框架默认 3 种；核心矛盾明显有更多或更少的维度时可以增减，并说明原因。选法：从核心矛盾出发，找出会把矛盾的不同一端当成首要问题的角色。只有在本题中确实会冲突时，才用"技术/商业/用户"这种通用组合。用领域角色（如"可靠性工程""渠道销售""监管合规"），不模仿或编造真实人物的观点。

**4.1 独立判断**：每个视角分别回答——怎样定义这个问题、最推荐什么路径、其他视角最容易忽略什么、什么证据会让它改变判断。

**4.2 交叉质疑**：让各视角互相质疑，写出共同认可的事实、真正的分歧、分歧背后的不同假设、最值得优先验证的关键假设。

- 各视角给出相同推荐时，检查是否选错了视角；真实的复杂问题很少各方一致。
- 不为共识而折中。分歧解决不了就保留，并说明哪个实验能裁决它。

### 五、综合结论

用八项表收尾：问题本质、现实经验、最推荐的方案、比较优势、适用条件、最大风险、停止条件、第一步实验。

- 推荐方案要能回溯到前面的证据，并说明它为什么胜过第一段推导出的其他路径和第四段里落败的视角。
- 停止条件要可观测（指标、时间点、事件），不要写"效果不好时"。
- 第一步实验要低成本、可逆，并写明：验证哪个关键假设、怎么做、多久、什么结果算通过、什么结果意味着换方案。

## 5. 贯穿全程的原则

- **证据标签**：关键判断标注【事实】（已验证，附来源或来自用户）、【案例】（他人经验，附来源）或【推测】（推理所得）。低档至少给第五段的判断加标签。
- **主动找反例**：每形成一个倾向性判断，就搜一次或想一次能推翻它的证据。
- **可证伪**：关键判断写明什么证据能推翻它。
- **现实可行**：推荐方案要考虑成本、资源、风险和实施条件，不推荐用户做不到的东西。
- **不为显得深刻而拉长**：某一段在本题中确实没有内容可写，就简短说明原因，比填充空话更有用。

## 6. 交付

- 输出用用户对话所用的语言。
- 低档和中档直接在对话里输出五段；存在会影响结论的未验证假设时，末尾加"附：未验证的关键假设"。
- 高档把完整报告写入用户指定的位置；未指定时写入当前工作目录下的 `analysis/YYYY-MM-DD-<主题>.md`，对话里只给八项结论表、最关键的分歧、第一步实验和文件路径。
- 结尾用一行写明本次档位，以及哪些完成标准没达到（例如"低档：案例凭记忆、未核实；需要可说'中档'或'高档'"）。全部达到就不用写。
