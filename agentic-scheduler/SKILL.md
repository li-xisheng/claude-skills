# Agentic Scheduler — AI 时代的排程与交付预测

## 世界观（为什么这套和传统排期不一样）

估算对象变了：过去估「人写代码要多久」，现在要预测的是**一个受验证带宽、共享资源队列、
未知分支和人类决策约束的动态系统何时收敛**。AI 是放大器不是均匀加速器——同样的工具在
不同任务/团队上的实测效果从 -19% 到 20x 散布，所以**诊断永远先于给数字**。
完整论证见 [references/methodology.md](references/methodology.md)。

## 五条铁律

1. **快慢分层**：慢变量（人的注意力上限、决策延迟、合同与合规门槛）可以内置进方法；
   快变量（模型能力、加速倍数、可自动验证比例）**一个都不许写死**——现场采集、
   2-4 周短窗校准、旧数据衰减。任何来自文献或记忆的加速数字只能当方向证据。
2. **探测优先**：能让 agent 试跑 30-60 分钟的任务，不要花 30 分钟猜。实测 > 估算。
3. **队列纪律为中枢**：真正的瓶颈是人的验证注意力。验证队列 WIP 上限、
   reviewer 利用率 ≤80%、保留 ~20% 应急容量。管好队列比估准数字更能缩短交付。
4. **数字必须带来源等级**：`实测` / `历史校准` / `推导` / `猜` 四级，禁止无标注的数字。
5. **一个模型三种视图**：内部预测 ≠ 运营看板 ≠ 対外承诺。
   永远不对不同受众发同一个数——尤其不要让 P50 流进合同。

## 第 0 步：适用性判断（先看要不要用这套）

**不适用**（直接做或口头给个区间，别启动流程）：单个小而清晰的任务、预计一次闭环、
低风险、无对外承诺。重流程用在小任务上反而比直接做慢一个数量级（有实测）。

**适用信号**（满足任一即启动）：≥3 个任务要排序 / 要对外承诺日期 /
多 agent 并行开发 / 含探索型任务 / 被问「AI 提效了为什么还要 X 周」。

## Phase 1：现场采集（先查后问）

自己能查的一律不问：repo 结构、issue/任务清单、**近期 merge 记录（这是现成的实测周期数据）**、
CI 配置、测试覆盖情况、团队构成线索。

查不到的才问，一轮 ≤4 个编号选择题、每个带推荐默认、可回「按默认」：

1. **验证带宽**：谁做 review/验收，每天能投入多少专注时间？（这是整个排程的分母）
2. **承诺刚性**：这次排期是内部参考 / 可 re-baseline 的承诺 / 有罚则的合同日期？
3. **实测数据**：最近 2-4 周有没有同类任务的实际周期记录？
   （有 → 经验分位数；没有 → 保守默认并标注`猜`，且把「取得前 3 个实测点」写进计划）
4. **沟通语境**：给谁看？（日本客户/受託開発 → 读 [references/external-layer.md](references/external-layer.md)）

## Phase 2：逐任务诊断（regime 分类）

对每个任务判三件事，这一步是整个方法的地基：

1. **Regime**（三选一）：
   - `一次成`：agent 大概率一次通过，验证轻（样板、迁移、有完整测试兜底的改动）
   - `反复磨`：预计 2-5 轮闭环（跨模块、共享文件、遗留代码、隐性业务规则）
   - `探索型`：方向本身未定（能不能做、选哪条路、偶发 bug 排查）

   辅助信号：预计 diff 大小、触及文件数、是否碰共享热点（auth/config/migration/schema）、
   新代码库还是遗留库、这活里「样板占比 vs 判断占比」。
   判断依据详见 methodology.md 第四节。

2. **残余人类注意力**（唯一需要人工估的量）：从头到尾读完/审完/测完/协调完这个改动，
   需要多少专注人类时间？`S`(≤1h) / `M`(半天) / `L`(1-2天)。**禁止 XL**——
   AI 让薄切分变便宜了，出现 XL 说明任务该拆。

3. **可探测性**：能安全 dry-run 的 → 直接排一个 30-60 分钟探测任务，用实测替代估算，
   探测报告看产物不听 agent 自评（agent 系统性高估自己：自报 77% 实际 22%）。
   探索型 → 给探索预算（总预算 20-30%）+ 预先写死的继续/杀死/转向条件。
   操作细节见 [references/mechanisms.md](references/mechanisms.md)。

## Phase 3：排程

1. **依赖 DAG + 文件触点**：标出任务间依赖和文件重叠（重叠即冲突风险，
   进 overlap registry，命中共享热点的无论多小都强制人审）。
2. **决策日历**：先排「哪天拍什么板」——人类决策点和不可逆节点才是排程骨架，
   工作在决策点之间浮动。把拍板尽量批处理，减少打断次数。
3. **队列纪律**：并行 agent 数由验证端拉动（验证队列满员就不开新任务），
   经验起点 3-5 路并行；reviewer 排程利用率 ≤80%，留 20% 吸收 Blocking 级发现。
4. **出日期**：有实测 → 按 regime 分类取经验分位数（P50/P80/P95）；
   无实测 → 保守推导 + 标注`猜` + 把校准计划写在最前面。
   不做逐任务缓冲叠加——分位数已含不确定性。
5. **开三本账**：技术发现 → 重估；需求变更 → Scope 版本升级；
   产品/方向学习 → Goal 版本升级。任何一本都不许被记成「研发延期」。

## Phase 4：输出三视图

先落**状态文件**（默认 `docs/schedule.md`，用户有偏好则从之），结构见 mechanisms.md 末节：
Goal(带版本) / Scope 契约 / 任务表(regime·注意力·来源等级) / 决策日历 / 队列规则 / ETA 修订日志(追加式)。

- **视图 1 内部预测**：P50/P80/P95 + 关键假设清单 + 高不确定项与其重估触发条件
- **视图 2 运营看板**：今天稀缺注意力给谁、验证队列水位、WIP 状态、
  发现分诊（Blocking → 吸入主线 / Important → 新 issue / Optional → backlog）
- **视图 3 対外承诺**：只出 **P80** + 前提·除外·受け入れ基準 + 预先约定的 re-baseline 触发条件。
  用三数并列（传统等价工作量 / 实际人投入 / 日历 ETA）回答「为什么不是 1/5」。
  格式与话术见 external-layer.md。

## Phase 5：持续重算（被再次呼出时）

读状态文件 → 收实测（完成任务的实际周期、闭环轮数）→ 更新经验分位数
（2-4 周滚动窗口，旧观测衰减——半年前的数据是上一代模型的数据）→ 重算 ETA →
追加修订日志，变化原因归入三本账。
ETA 变化像 GPS 导航：有依据的修订是预测系统在正常工作，不是排期失败——
真正要盯的是预测区间是否随信息增加而收敛。

## 防坑清单

- **缓冲不叠加**：用了分位数就不再加统一 buffer；总缓冲若超 50% 必有重复计算。
- **软约束击穿警报**：验证队列爆掉时，团队的自然反应不是延期而是零审查合并硬撑
  （实测：队列压力下零审查合并 +31%、事故率 +242%）。WIP 上限就是防这个的，不许为赶进度临时撤除。
- **スコープ蠕動**：交付越快，客户「顺便加个这个」越多。Out of Scope 条款先写好。
- **防 Goodhart**：过程指标（AI 介入占比、PR 数）必须和结果指标（已验证交付周期）成对看，
  任何单指标都会被 hack。
- **别打磨 spec 排版**：实证显示指令文件的大小/结构/位置对遵循率无影响，
  显著的是任务/会话长度——投资方向是把任务切小，不是把文档写漂亮。
