# 治理机制手册（操作层）

各机制的落地细节。原理与证据见 methodology.md，此处只讲怎么做。

## 1. 探测协议（Probing）

**什么时候探**：任务可在沙箱/分支安全试跑、且 30-60 分钟探测费 < 估错的代价。
探索型任务必探；「一次成」候选抽查探；碰共享热点的必探。

**怎么探**：给 agent 一个 timebox（30-60 分钟），让它在真实代码库上尝试该任务或其最薄切片。
产出**探测报告六因子**：
1. 审查负荷（预计 diff 大小、触及文件数）
2. 认知负荷（reviewer 需要理解多少新上下文）
3. 爆炸半径（改动影响面、回滚难度）
4. 测试负担（现有测试覆盖情况、需新增什么）
5. 协调成本（和哪些进行中任务有文件/接口重叠）
6. 风险不可逆性（碰不碰数据、迁移、生产配置）

**铁则：看产物不听自评**。agent 系统性高估自己（自报成功率 77%，实测 22%）。
以 diff、测试结果、能否运行为准；用对抗式提问校准（「假设这个方案会失败，最可能死在哪」）。

**探索型任务额外要求**：探测预算 ≤ 总预算 20-30%；开工前写死三个条件——
继续条件、杀死条件、转向条件；ETA 旁并列报 PTS（这条路成立的概率），
方向不确定性与工期不确定性分开报。

## 2. 经验分位数校准（替代蒙特卡洛）

1. 按 regime（一次成/反复磨/探索型）分桶收集**实际周期**（任务启动→合并）与**闭环轮数**
2. 每桶取经验 P50/P80/P95——样本 ≥5 个才可信，<5 个标注`推导`
3. **滚动窗口 2-4 周**，旧观测衰减（半年前的数据是上一代模型的数据）
4. 无任何实测时的冷启动：给保守区间 + 全部标注`猜` + 把「取得前 3 个实测点」列为计划第一项

**来源等级标注（每个数字必带）**：
- `实测`：本团队、当前模型、≤4 周内的观测
- `历史校准`：本团队更早的数据（注明 vintage）
- `推导`：由静态信号或类比推出
- `猜`：无依据的保守假设

注意「自报实测」要降级——人的自报耗时有 ~39pp 的系统性感知偏差，尽量用时间戳（PR 创建→合并）。

## 3. 队列纪律

- **CONWIP 拉式**：设验证队列上限 N（起点：reviewer 数 × 每人同时可跟的任务数，通常 2-3）。
  队列满员 → 不启动新 agent 任务，把产能转向清队列或探测。
- **利用率红线**：reviewer 的**计划占用 ≤80%**。排到 90% 不是高效，是等待时间爆炸的前夜。
- **应急块**：~20% 注意力不排任何计划，专门吸收 Blocking 级发现。用不完就顺延，不许预支。
- **加急限额**：插队任务 ≤ 总量 5%。第 2 个「特急」出现时，要求发起人先降级一个已有加急。
- **帕累托审查分级**：按静态信号（diff 大小、触点文件数、是否碰热点）给 PR 分 P0-P3；
  P0-P1 逐行全审，P2 略读 + 验证测试，P3 CI 绿即自动批准。全审最险 20% 即覆盖 ~69% 审查量。

## 4. 决策日历

1. 列出计划期内所有**人类拍板点**（方案选型、验收、发布 go/no-go）和**不可逆节点**（迁移、对外发布、删除）
2. 给每个拍板点定日期与拍板人——这是排程骨架，任务在其间浮动
3. **批处理拍板**：把同类小决策攒到固定时段（如每日一次 15 分钟），不随到随拍；
   给 agent 的指令装载更多前置判断，让其自主链更长
4. 拍板点延误直接平移下游 ETA——决策延迟是最真实的关键路径

## 5. 并行治理

- **并行生成、串行合并**：生成端保持并行，merge 强制单线程排队；每次合并后跑行为验证再放行下一个
- **Overlap Zone Registry**：显式登记高风险共享文件（auth、config、migration、schema、共用工具层）。
  任何任务命中登记项 → 无论风险分级结果如何强制人审，且同一时刻只允许一个任务碰同一登记项
- **Worker/Validator 分层**：批量执行用便宜模型，验证判断切贵模型——验证成本部分转移给 AI
- **每个 agent 一个 scope boundary**：不让单 agent 同时碰前端和后端（除非任务明确跨界）；
  后台 agent 只派低判断力任务（测试生成/文档/lint/依赖审计），高判断力任务留给前台交互

## 6. 发现分诊

开发中冒出的新问题，就地三选一，不许悬空：

| 级别 | 判据 | 动作 | 记账 |
|---|---|---|---|
| Blocking | 不解决无法交付 | 吸入当前任务，消耗应急块 | 技术发现 → 重估 |
| Important | 影响质量但能上线 | 开新 issue，进下轮排程 | 技术发现 → backlog |
| Optional | 顺手可优化 | 进 backlog，禁止顺手修 | 不记账 |

需求方新增要求走另一本账（Scope 版本升级），见 external-layer.md。

## 7. 状态文件模板

默认落在 `docs/schedule.md`（用户有偏好从之）。骨架：

```markdown
# <项目名> 排程 — Goal v<N> / Scope v<N>
更新：<日期>（第 <N> 次修订）

## Goal（当前版本）
<干完世界什么样，一句话。历史版本折叠在文末>

## Scope 契约
前提： / 除外（Out of Scope）： / 受け入れ基準：

## 任务表
| 任务 | regime | 注意力 | 依赖/触点 | 状态 | 周期(来源等级) |

## 决策日历
| 日期 | 拍什么板 | 拍板人 |

## 队列规则
验证 WIP 上限：N ／ reviewer 利用率红线：80% ／ 应急块：20%

## 当前预测（内部视图）
P50: <日期> ／ P80: <日期> ／ P95: <日期>
关键假设： / 高不确定项与重估触发条件：

## 发现池
Blocking: / Important: / Optional:

## ETA 修订日志（追加式，每条注明归入哪本账）
- <日期> P80 从 X → Y。原因：<技术发现/需求变更/产品学习>：<一句话>
```

维护责任在 AI（本 skill 被呼出时读取-更新-追加），人只审阅。
记账若超过 5 分钟/天，说明字段过多，砍到核心三项（regime、注意力、对外承诺与否）。
