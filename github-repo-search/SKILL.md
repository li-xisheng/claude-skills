# GitHub 分波筛查

核心原则：**漏掉大项目比多看几个候选代价大得多**。一个成熟大项目的存在，可能直接决定一个产品该不该做，而且它里面有大量被众人验证过的实现可以借鉴。所以召回优先，宁可多搜几路。低星项目常见问题是 README 吹得好、实际不可用，只作补充，且必须过可用性验证。

一律用已登录的 `gh` CLI（不用匿名 API，避免限额）。不需要先找用户确认需求；需求明显含糊时最多问一句。

## 先选深度

搜索成本差异很大（快速约 5–10k tokens，完整约 40–80k），按"漏掉大项目的代价"选档。用户明确说了"快速/随便看看/深挖/认真查"时以用户为准。

| 档位 | 什么时候用 | 做哪些 |
|---|---|---|
| **快速** | 开发中顺手找参考实现、查某个库怎么用、已知大致方向只想确认 | 第 1 波的第 1 路（已知头部清单）+ 第 3 路（短关键词）各跑一下，不读 README，不做重合度检查。结果列 3–5 个即可，末尾注明"快速档，可能有遗漏，需要可说'深挖'" |
| **标准**（默认） | 用户主动问"有没有开源项目/类似的" | 第 1 波六路全跑，但滚雪球只读 1 个项目、网页搜索 2 组；做重合度检查，不补搜；需要时才下探第 2、3 波 |
| **深挖** | 决定一个产品/功能要不要做、技术选型、用户说"认真查""别漏" | 全流程：六路 + 重合度检查 + 补搜 1 轮 + 第 2、3 波，交付中必须回答"是否已有成熟方案" |

拿不准时：涉及"要不要做/选哪个"的用深挖，只是"找个写法参考"的用快速。快速档发现了明显的大项目竞品时，提醒用户是否要升到深挖。

## 为什么单一渠道会漏

每个渠道都有固定盲区，而且盲区不重合：
- **GitHub 搜索**只匹配仓库名、描述、topic，不搜 README。实测："browser automation agent" 漏掉全部 6 个头部项目；"微信 聊天记录" 漏掉 4.2 万★的 LC044/WeChatMsg（描述为空）和 3.9k★的 WeChatDataAnalysis。
- **网页搜索**能补回上面这些，但会混入 1★ 的仿冒仓库，且排名靠前。
- **自身知识**覆盖不了训练截止后出现的新项目。

所以召回要多路合并，并用"多路是否命中同一批项目"来判断是否找全。

## 第 1 波：高星（stars ≥ 1000），六路召回

1. **已知头部清单**（最重要）：先凭自身知识列出该领域公认的主流项目 5–10 个，逐个 `gh api repos/<owner>/<repo> --jq '"\(.stargazers_count) \(.full_name) \(.pushed_at)"'` 核实存在、星数和活跃度。这一路专门补关键词搜不到的大项目。
2. **topic 搜索**：猜 2–4 个 topic 名（如 `browser-automation`、`web-scraping`、`llm-agent`）
   ```bash
   gh search repos --topic <topic> --stars ">=1000" --sort stars --limit 15 \
     --json fullName,stargazersCount,description,updatedAt
   ```
3. **短关键词搜索**：每组只用 1–2 个词，多换几组同义词（中英文都试），不要堆 3 个以上的词
   ```bash
   gh search repos "<1-2 个词>" --stars ">=1000" --archived=false --sort stars --limit 15 \
     --json fullName,stargazersCount,description,updatedAt
   ```
4. **awesome 合集**：`gh search repos "awesome <主题>" --sort stars --limit 5`，读排名第一的合集的 README，提取里面列出的项目
5. **网页搜索**：用 WebSearch 搜 2–3 组，如 `<主题> github open source`、`<主题> 开源 github 推荐`（中文领域必搜中文）、`best <主题> library 2026`。从结果中提取 `github.com/<owner>/<repo>` 链接，**逐个用 `gh api` 回查星数**，网页里的排名和描述不作数。
6. **滚雪球**：对已确认匹配的前 2–3 个项目，读 README 中的 Alternatives / Comparison / Related projects / Inspired by / 致谢 段落，以及 awesome 合集中同类条目，把提到的仓库加入候选。大项目通常会和其他大项目对比，这一路专门补新出现、自己不知道的项目。

合并去重后**逐个判断是否真正匹配需求**（看 description 和 README 开头，不只看关键词命中）。

### 判断是否找全（重合度检查）

记录每个候选来自哪几路。看匹配项目中星数最高的前 3 个：
- 都被 ≥2 路命中 → 召回基本可靠，结束扩展。
- 有项目只被 1 路命中 → 说明其他渠道有盲区，用它的名字和 README 里的措辞再搜一轮（换成它描述里用的词做短关键词、看它的 topic），并对它做滚雪球。最多补 1 轮。
- 所有渠道都只找到同一批小项目 → 不要当成"已找全"，在报告里明确标注"该方向可能太新，召回不可靠"。

- 有 ≥1 个真正匹配 → 进入交付；可视情况跑第 2 波补充对比，但不再下探第 3 波。
- 没有匹配 → 在报告中写明"第 1 波无匹配：搜了哪些词、看了哪些高星仓库、为什么不匹配"，进入第 2 波。

## 第 2 波：中星（100 ≤ stars < 1000）

同样的 topic 和短关键词，过滤条件改为 `--stars "100..999"`（第 3 波为 `--stars "10..99"`）。处理方式同第 1 波。

## 第 3 波：低星（10 ≤ stars < 100，仅在前两波都无匹配时）

低星项目**默认不可信**，每个候选必须过下面的可用性验证，至少满足 4 条才能列入结果：

1. 最近 6 个月内有 commit
2. 有可执行的安装/快速开始步骤（不是只有愿景描述）
3. 有示例、测试或 CI 中的至少一项
4. 有 release/tag 或已发布到包管理器（npm/PyPI 等）
5. issue 中没有大量"不能用/跑不起来"且无回应
6. 核心功能有实际代码实现（看主要源码文件，不是空壳或只有接口）

验证方法：`gh api repos/<r>`、`gh api repos/<r>/commits?per_page=5`、`gh api repos/<r>/releases?per_page=3`、读 README 和主要源码。

通过者标注"⚠ 低星，已验证"；未通过但有可借鉴思路的，只能写"仅参考思路：<具体可借鉴的部分>"，不得作为推荐。

stars < 10 的项目不列入结果。

## 交付格式

1. 检索词清单
2. 每一波的结果概要（召回数 / 匹配数 / 未匹配原因）
3. 推荐表格：

| 仓库 | ★ | 最近更新 | 命中路数 | 是什么 + 为什么推荐 | 风险/限制 |
|---|---:|---|---|---|---|

4. **是否已有成熟方案**：先用一句话回答"这个方向是否已经有成熟的主流项目覆盖了需求"。如果有，说明它覆盖了需求的哪些部分、哪些没覆盖，供用户判断"还要不要自己做"。
5. 结论：最推荐哪个；若只能推荐低星项目，明确说明"该方向没有成熟的主流项目"。
6. 召回可信度：重合度检查的结果，以及可能存在的遗漏。

## 禁止

- 只用 `gh search code` 的结果做推荐（它不按星数排序，容易全是小仓库）
- 采用网页搜索结果而不用 `gh api` 回查星数
- 第 1 波没跑完就看低星项目
- 未经验证就推荐 stars < 100 的项目
